# Criterios de aceptación del frontend

## Alcance y uso

Estos criterios verifican [frontend.specs.md](frontend.specs.md) y las tareas de [frontend.tasks.md](frontend.tasks.md), bajo las restricciones de [AGENTS.md](../AGENTS.md) y el contrato de [API-DOCS/openapi.yaml](../API-DOCS/openapi.yaml). Cada identificador `FE-XX` debe tener evidencia al implementar el cliente. El usuario autorizó la implementación del frontend; cada criterio se acepta después de ejecutar su comprobación, no por estar documentado.

Los criterios de la tabla editable de **Calificaciones** se verifican sobre la implementación del cliente y sus pruebas.

Las comprobaciones funcionales usan las respuestas y reglas del backend. Las validaciones del cliente orientan al usuario, pero no sustituyen los rechazos de la API. Los casos con datos persistidos y los recorridos de extremo a extremo se ejecutan en Docker con datos de prueba separados de la base de desarrollo.

## Base técnica, contrato y organización (tareas 1 a 3)

- **FE-01 — Entorno operativo.** Desde los comandos documentados se levantan frontend, backend y MySQL en Docker; el cliente llega a la API mediante `/api` y la comprobación pública `GET /api/healt` responde según el estado del servidor y MySQL. **Evidencia:** ejecución reproducible y comprobación de red desde el frontend.
- **FE-02 — Stack y responsabilidades.** El cliente usa JavaScript, Vite, React, Tailwind CSS, Motion y `fetch` nativo. Páginas, componentes, acceso a la API y utilidades están separados por responsabilidad; no hay conexión directa a MySQL ni dependencias añadidas sin necesidad justificada. **Evidencia:** revisión del código y de las dependencias.
- **FE-03 — Conformidad HTTP.** Los cuerpos enviados, campos leídos, roles, códigos de respuesta y errores de cada flujo implementado coinciden con OpenAPI y con la API real. La descarga `.xlsx` se trata como respuesta binaria. **Evidencia:** pruebas de integración del cliente con la API y revisión de correspondencia con el contrato.
- **FE-04 — Estados y errores comunes.** Las vistas pertinentes muestran carga, vacío, éxito y error. Ante `400`, `401`, `403`, `404`, `409`, `500` o un fallo de red, muestran un mensaje útil y no anuncian una operación como guardada si fracasó; los datos de un formulario rechazado permanecen disponibles para corregirlos. **Evidencia:** pruebas de componentes e integración con respuestas y fallos simulados o reales.
- **FE-05 — Datos decimales y nulos.** Los valores recibidos se presentan con dos decimales de forma consistente. Una nota `null` se indica como «sin calificar» y una nota `0,00` como calificada con cero; el cliente presenta porcentajes de la API sin aplicar reglas propias de reparto, truncamiento o resultado. **Evidencia:** pruebas unitarias de las utilidades con lógica propia y pruebas de componentes con ambas notas.

## Identidad y navegación (tareas 2 a 4)

- **FE-06 — Inicio de sesión.** Profesor y estudiante usan el mismo formulario de correo y contraseña. El cliente envía el correo con las mayúsculas y minúsculas escritas, recibe el JWT y abre el área indicada por `rol`; las credenciales rechazadas no abren sesión. **Evidencia:** pruebas de formulario, integración y extremo a extremo de ambos roles.
- **FE-07 — Vigencia y cierre de sesión.** Una recarga antes del vencimiento mantiene la sesión; al vencer la hora de vigencia, recibir un `401` de una ruta protegida o elegir **Cerrar sesión**, el cliente retira el token y deja de mostrar datos protegidos. Un `403` informa falta de permiso sin conceder acceso a otro rol. **Evidencia:** pruebas unitarias del manejo temporal y de estado, pruebas de componentes e integración con token vigente y vencido.
- **FE-08 — Permisos y secretos.** Las vistas del profesor no están disponibles para un estudiante y las del estudiante no presentan datos de otro usuario. El frontend no muestra ni registra hashes, JWT en mensajes, credenciales de base de datos ni clave de firma. **Evidencia:** pruebas por rol y revisión del código, consola y archivos preparados para Git.
- **FE-09 — Identidad visual.** La cabecera y el acceso muestran «Sistema de Notas Parciales». Se usa la paleta provisional y la densidad equilibrada de `frontend.specs.md`, sin representarlas como marca oficial. Texto, estados, botones y formularios son legibles y el color no es la única indicación de un estado. **Evidencia:** revisión visual en computadora y celular.
- **FE-10 — Navegación del profesor.** Tras iniciar sesión, el profesor llega a **Cursos**. El menú lateral de escritorio contiene Cursos, Cuatrimestres, Catálogo de actividades, Estudiantes y Cerrar sesión. Dentro del curso elegido aparecen Componentes, Matrícula, Calificaciones, Asistencia y Concentrado; el cuatrimestre, código y número de grupo identifican el contexto. **Evidencia:** pruebas de navegación con dos grupos que comparten código.

## Funciones del profesor (tareas 4 a 9)

- **FE-11 — Cuatrimestres y cursos.** El profesor consulta y crea cuatrimestres con código y fechas exactamente separadas por 98 días, y cursos con nombre, código, cuatrimestre y grupo. Un curso con código repetido se distingue por cuatrimestre y grupo; otra duración o campos inválidos se muestran como error sin crear un registro aparente. **Evidencia prevista para la automatización:** pruebas de formularios e integración con la API.
- **FE-12 — Eliminación de curso.** La acción muestra una confirmación que explica la eliminación de matrículas, componentes, calificaciones y asistencia del curso. Cancelar no envía el borrado; un rechazo conserva el curso en la vista; una respuesta exitosa actualiza la lista. **Evidencia:** pruebas de componentes e integración para cancelar, rechazar y confirmar.
- **FE-13 — Catálogo.** El profesor puede consultar, crear, editar y eliminar actividades libres. «Indagación y exposición» figura como una opción; nombres duplicados aunque cambien mayúsculas o tildes muestran el conflicto de la API. Si `en_uso` es `true`, editar y eliminar están bloqueados y el estado se actualiza cuando cambian sus asociaciones. **Evidencia:** pruebas de componentes e integración para opción libre, usada y conflicto concurrente.
- **FE-14 — Componentes.** El formulario solicita **Puntaje por actividad** de `1,00` a `100,00`, con hasta dos decimales, y envía `puntaje_por_actividad`; la creación exitosa muestra el porcentaje y puntaje de cada actividad según la API. Con `10,00 %`, `10,00` puntos por actividad y cinco actividades, muestra cinco veces `2,00 %` y `10,00` puntos; con tres, tres veces `3,33 %` y `10,00` puntos. Solo el residuo porcentual se descarta. Un componente histórico muestra su puntaje individual vigente, incluida la corrección puntual de **Tareas**, sin que la vista altere notas. **Evidencia:** pruebas de límites, rechazo por suma superior a 100 %, integración del reparto porcentual y consulta de datos históricos.
- **FE-15 — Matrículas.** El profesor consulta estudiantes y matriculados, registra nombre, dos apellidos y correo, y puede matricular a una cuenta existente sin duplicarla. Conserva la grafía del correo y muestra rechazos por duplicado, dominio no permitido o correo del profesor. Tras matrícula tardía, al consultar la asistencia aparecen como `justificado` solo las sesiones cuya asistencia ya estaba registrada; las pendientes siguen sin condición. **Evidencia prevista para la automatización:** pruebas de formularios e integración en dos cursos con sesiones registradas y pendientes.
- **FE-16 — Contraseña generada.** El profesor selecciona un estudiante y ve la contraseña devuelta por la operación de generación para comunicársela por correo. La interfaz no envía el correo por sí misma, no muestra hashes y no conserva esa contraseña en vistas posteriores. **Evidencia:** prueba de componentes y revisión de datos mostrados y registrados.
- **FE-17 — Captura de nota y observación.** En **Calificaciones**, el profesor ve una tabla editable del curso y grupo abiertos, con estudiantes matriculados en filas y actividades individuales en columnas. Cada celda identifica una matrícula y actividad concretas, ofrece un campo `type="number"`, acceso a un editor de observación y un control de guardado con icono de disquete cuyo nombre accesible identifica esa relación. Al abrir el editor se muestra la observación vigente. El valor inicial diferencia `null` de `0,00`; una observación sin nota válida no se guarda. Se rechazan puntos fuera de rango y observaciones de más de 125 caracteres. **Evidencia:** pruebas de componentes e integración con varios estudiantes, actividades y grupos.
- **FE-17A — Guardado y porcentaje por celda.** Los valores iniciales proceden del concentrado vigente y los puntajes máximos de los componentes del curso. Abrir el editor de observación no sobrescribe valores editados sin guardar. Cada disquete envía por la ruta individual la nota y observación de su celda únicamente; otras celdas modificadas siguen pendientes. Tras éxito, se muestra debajo de la nota el porcentaje **obtenido** devuelto por la API; mientras hay cambios pendientes, el porcentaje anterior no se presenta como cálculo provisional. Un rechazo o fallo de red informa el motivo sin anunciar éxito ni asignar el cambio a otra celda. **Evidencia:** pruebas de componentes, integración y extremo a extremo con muchas notas, errores y dos grupos del mismo código.
- **FE-17B — Cambios sin guardar.** Si hay celdas editadas sin guardar, cambiar de pestaña o salir del curso muestra una advertencia con opciones de continuar editando o salir descartando los cambios. No se envía un guardado automático; guardar una celda no descarta ni guarda las demás. La tabla permite teclado y foco visible, desplazamiento horizontal en celular y uso legible en temas claro y oscuro. **Evidencia:** pruebas de navegación y de componentes con varias celdas pendientes, más revisión visual en ambos tamaños y temas.
- **FE-18 — Porcentaje mostrado.** Para una actividad de 10 puntos y 2 %, una nota de `8,50` muestra `1,70 %` obtenido según la API. Las actividades sin nota aportan cero al resultado que entrega el backend; el cliente no recalcula ese resultado. **Evidencia:** prueba de integración y de presentación de la respuesta real.
- **FE-19 — Sesiones y asistencia.** El profesor ve quince sesiones programadas con número, fecha y estado; elige una sin control de fecha ni «Nueva sesión». El primer guardado y las correcciones usan `PUT` sobre esa sesión con una condición por matrícula, incluidas las inicialmente justificadas por matrícula tardía. La interfaz informa condiciones faltantes o rechazos de la API y no habilita guardar sin estudiantes. **Evidencia prevista para la automatización:** pruebas de formulario e integración para primer registro y edición.
- **FE-20 — Concentrado del profesor.** Para un curso y grupo por vez, la tabla presenta estudiantes en filas y actividades en columnas, con nota y porcentaje obtenido por celda. No mezcla grupos con el mismo código ni añade puntaje máximo, observaciones o total del curso a la tabla; actualiza datos tras cambios relevantes. **Evidencia:** pruebas de componentes e integración con dos grupos y una nota modificada.
- **FE-21 — Descarga `.xlsx`.** Solo el profesor dispone de la acción de descarga. La solicitud autenticada obtiene el archivo del curso y grupo seleccionados; un fallo de red o de API se informa sin producir un archivo presentado como válido. **Evidencia:** prueba de integración de la respuesta binaria y recorrido completo de descarga.

## Funciones del estudiante (tarea 10)

- **FE-22 — Navegación del estudiante.** Tras iniciar sesión, se presenta **Mis cursos**. Su menú contiene Mis cursos, Perfil y Cerrar sesión; al entrar a un curso aparecen Calificaciones, Asistencia y Concentrado. No se muestran controles del profesor. **Evidencia:** pruebas de navegación por rol y extremo a extremo.
- **FE-23 — Tarjetas y resultado.** Cada tarjeta muestra el título del componente separado del rótulo de su actividad individual, además de nota, porcentaje efectivamente obtenido y observación cuando exista; el curso muestra el resultado recibido de la API. Una nota pendiente se diferencia de `0,00`; si el aporte es `1,70 %`, se muestra ese valor y no el peso completo de `2,00 %`. **Evidencia:** pruebas de componentes e integración.
- **FE-23A — Rótulo de actividad del estudiante.** Si `cantidad_actividades = 1`, el rótulo superior muestra únicamente `actividad_catalogo`, por ejemplo «proyecto», sin «Actividad 1» ni número. Si `cantidad_actividades > 1`, muestra `actividad_catalogo` seguido de un espacio y el `numero` de esa actividad dentro del componente; con catálogo «tarea» y título de componente «Tareas», aparecen «tarea 1» y «tarea 2». El título «Tareas» permanece en su lugar separado; otro componente reinicia su propia numeración. No se deriva el nombre del título, no se singulariza y se conserva la grafía del catálogo. **Evidencia:** prueba de componentes para ambos tamaños y dos componentes distintos, prueba de integración que comprueba ambos campos en cada tarjeta de la API y revisión de OpenAPI.
- **FE-23B — Observación condicional.** Una tarjeta con `observacion` no vacía muestra el rótulo «Observación» y el texto recibido. Con `observacion: null`, `""` o texto compuesto solo por espacios, la tarjeta no contiene ni el rótulo ni contenido o mensaje de reemplazo. Las demás partes de la tarjeta siguen visibles y el campo de la API permanece igual. **Evidencia:** prueba de componentes con los cuatro casos y recorrido del estudiante con una tarjeta que tenga observación y otra que no la tenga.
- **FE-24 — Asistencia propia.** En cada curso, el estudiante ve únicamente las fechas y condiciones `presente`, `ausente` o `justificado` ya registradas para su matrícula; las sesiones programadas pendientes no aparecen. **Evidencia prevista para la automatización:** prueba de integración con una sesión pendiente, dos estudiantes y más de un curso.
- **FE-25 — Concentrado propio.** El estudiante ve una tabla por curso con sus notas y porcentajes obtenidos por actividad. No se incluyen observaciones, puntaje máximo ni total del curso en esa tabla, ni existe descarga `.xlsx` para su rol. **Evidencia:** pruebas de componentes e integración con varios cursos.
- **FE-26 — Cambio de contraseña.** Desde **Perfil > Cambiar contraseña**, el estudiante envía la nueva contraseña y recibe confirmación o rechazo comprensible. El cliente no muestra ni almacena el hash. **Evidencia:** prueba de formulario e integración con la API.

## Adaptación, calidad y pruebas (tareas 2 y 11)

- **FE-27 — Uso en celular.** El menú lateral del profesor se abre mediante un botón y puede cerrarse. Las pestañas de curso ocupan una fila desplazable. Ambos concentrados permiten desplazamiento horizontal para consultar todas las columnas sin ocultarlas. **Evidencia:** pruebas de componentes y revisión en tamaños de computadora y celular.
- **FE-28 — Accesibilidad básica.** Inicio de sesión, menús, pestañas, formularios, confirmación de eliminación y tablas se pueden recorrer con teclado; el foco y las etiquetas son visibles, y errores y estados se expresan también con texto comprensible. **Evidencia:** revisión manual de teclado y comprobaciones automatizadas de componentes donde sean pertinentes.
- **FE-29 — Pruebas unitarias.** Las funciones auxiliares con lógica propia tienen casos normales, límites y errores: representación de cadenas decimales, `null` frente a cero, interpretación de respuesta HTTP y vigencia de sesión. No se crean pruebas que solo repitan detalles triviales de implementación. **Evidencia:** suite unitaria ejecutada en Docker y resultado registrado.
- **FE-30 — Pruebas de componentes.** Formularios, navegación por rol, tarjetas, concentrados, confirmaciones y estados de carga, vacío y error se verifican con interacciones de usuario y respuestas controladas. **Evidencia:** suite de componentes ejecutada en Docker y resultado registrado.
- **FE-31 — Pruebas de integración y contrato.** Los flujos del cliente se prueban frente a la API del proyecto y OpenAPI: autenticación, JWT, observaciones previas, `en_uso`, matrículas, calificaciones, asistencia, concentrados y descarga. Se comprueba que los campos consumidos y los errores correspondan al contrato. **Evidencia:** suite de integración ejecutada en Docker con base de prueba separada.
- **FE-32 — Pruebas de extremo a extremo.** Un recorrido del profesor cubre acceso, curso, componente, matrícula, varias notas guardadas por celda, observación, advertencia por cambios pendientes, asistencia, concentrado y descarga; uno del estudiante cubre acceso, cursos, tarjetas, asistencia, tabla, cambio de contraseña y salida. Se prueban también recarga antes del vencimiento y salida al vencer el JWT. **Evidencia:** recorridos automatizados repetibles dentro de Docker.
- **FE-33 — Repetibilidad y entrega.** Las pruebas pueden repetirse sin alterar datos de desarrollo; sus comandos están documentados. Antes de aceptar el frontend, pasan las suites pertinentes y la revisión visual de computadora y celular, y se confirma que no hay secretos versionados. **Evidencia:** comandos, resultados y revisión del estado de Git.
- **FE-34 — Cambio de tema.** Un botón con iconos de sol y luna aparece en el acceso y en las áreas del profesor y del estudiante, en computadora y celular. Parte del tema claro cuando no hay preferencia guardada y alterna inmediatamente entre claro y oscuro sin perder formularios, datos ni navegación. La elección persiste al recargar y al cerrar sesión; todos los componentes y estados siguen siendo legibles, incluido el foco de teclado. El botón tiene un nombre accesible que indica el tema al que cambiará y se puede activar con teclado. **Evidencia:** pruebas unitarias y de componentes de cambio y persistencia, más revisión visual de ambas variantes en acceso, vistas autenticadas, tablas y celular.

## Eliminación de componentes (tarea 12)

Los criterios FE-35 a FE-38 se verifican con las pruebas de componentes y el recorrido de extremo a extremo contra la API y la base temporal de Docker.

- **FE-35 — Confirmación siempre.** El profesor dispone de **Eliminar** en cada componente del curso y ve un cuadro propio de la aplicación antes de cualquier `DELETE`, también cuando no hay notas. El cuadro identifica el curso y el componente y comunica qué registros se pierden y cuáles permanecen. Cancelar no solicita el borrado. No se usan `alert()` ni `confirm()` de JavaScript. **Evidencia prevista:** pruebas de componentes y revisión de teclado, foco, celular y temas claro y oscuro.
- **FE-36 — Advertencia por notas.** Si `tiene_calificaciones` es `true`, la confirmación advierte que el componente está en uso y que se perderán notas y observaciones; incluye el caso de nota `0,00` y permite confirmar. La solicitud lleva `confirmar_con_notas=true` solo tras esa confirmación. Ante `409` por una nota nueva, se muestra otra advertencia y se requiere una nueva decisión del profesor. **Evidencia prevista:** pruebas con nota positiva, cero y cambio concurrente.
- **FE-37 — Resultado y errores.** Tras un borrado exitoso desaparece el componente sin borrar curso, matrícula, asistencia ni otros componentes; se refrescan catálogo, calificaciones y concentrados según corresponda. Si la API rechaza o falla la solicitud, el componente permanece visible y se informa el motivo. **Evidencia prevista:** integración y recorrido de extremo a extremo con datos aislados, incluido `en_uso` compartido.
- **FE-38 — Rol y contrato.** El estudiante no ve la acción ni puede solicitar el borrado. El cliente consume `tiene_calificaciones` y la ruta `DELETE` exactamente como figuran en OpenAPI. **Evidencia:** prueba por rol y verificación de contrato y rutas.
